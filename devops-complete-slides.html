⏱ Session 1 — What is DevOps?

The Problem — Dev vs Ops Silos

😤 Development Team

  • Goal: ship new features fast
  • Works on their own laptop
  • Says: "Works on my machine!"
  • Throws code over the wall to Ops
  • Moves on to next feature

😤 Operations Team

  • Goal: keep production stable
  • Receives code without warning
  • Different environment from Dev
  • Says: "It breaks our servers!"
  • Deployment takes days

Without DevOps

  • Release once a month or less
  • Deployment takes 2–3 days manually
  • Bugs reach production often
  • Teams blame each other
"Integration Hell" — teams build in isolation for weeks. When they combine: conflicts everywhere. Nobody knows whose code broke what. Untangling takes days.
⏱ Session 1 — What is DevOps?

What is DevOps?

DevOps is a culture, mindset, and set of practices that brings Development and Operations together — automating the software delivery process so teams can build, test, and release software faster and more reliably.

🤝

Collaboration

Dev and Ops share ownership — same team, same goals, same on-call.

🤖

Automation

Every manual step from code to production is automated.

🔁

Fast Feedback

Know within minutes if something broke — not days later.

Remember: DevOps is NOT a job title. It's an organisation-wide philosophy. Dev + Ops + Security + QA — everyone participates.
⏱ Session 1 — The Infinity Loop

The DevOps Infinity Loop ∞

Shaped like ∞ because it never stops — every Monitor finding loops back to Plan

Left side — Dev 💙

Plan → Code → Build → Test. Developer activities. Every step feeds the next automatically.

Right side — Ops 💚

Release → Deploy → Operate → Monitor. Monitor feeds back to Plan — loop never ends.

⏱ Session 2 — Git's Role

Feature Branch Workflow

main:    ──●──────────────────────────────────●── always deployable
             \                                /
feature:  ●──●──● (dev works here)    PR opened → CI ✅ → reviewed → merge

Main branch

  • Always deployable
  • Protected — no direct push
  • Only accepts PRs that pass CI

Feature branch

  • One branch per feature/bugfix
  • Short-lived — merge quickly
  • Isolated from other work

Pull Request

  • Code review gate
  • CI must pass to merge
  • Approval required before merge
Rule: Nobody pushes directly to main. Every change goes through a PR. CI runs. Someone reviews. Then it merges. This is what keeps main always deployable and production always stable.

CI = automatically build and test every code change the moment it's pushed — multiple times per day, every day, zero human involvement.

⏱ Session 3 — CI/CD

Continuous Delivery vs Deployment

Continuous Delivery

Always ready to deploy — human decides when to ship.

  • Pipeline builds + tests + stages
  • Waits for human approval
  • Human clicks "Deploy to Production"

Used in: banking, healthcare, regulated

Continuous Deployment

Automatically deployed to production when CI passes.

  • No approval needed
  • Merge to main = live in prod
  • Deploy 100x per day

Used in: Netflix, Spotify, SaaS

⏱ Session 3 — Pipeline Anatomy

Anatomy of a CI/CD Pipeline

A pipeline = sequence of stages. Each is a gate — fail one, stop everything.

Trigger
git push
→
Test
mvn test
→
Build
mvn package
→
Artifact
.jar stored
→
Deploy
cf push

Trigger

A push, PR, or scheduled time starts the pipeline. Our YAML: on: [push, pull_request]

Test → Build (CI)

Test first — if tests fail, skip build. CI stages run on every push. needs: creates the dependency chain.

Artifact → Deploy (CD)

Artifact is stored, then deployed. CD stages only run on merge to main. Build once, deploy everywhere.

Artifact: The built output — our devops-demo-app-1.0.0.jar. Build once, store it, deploy to dev → QA → prod. Never rebuild for each environment.
⏱ Session 3 — Our Pipeline

Our Actual Pipeline — .github/workflows/ci-cd.yml

# Trigger — what fires the pipeline
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:               # Job 1
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-java@v3
      - run: mvn test -f app/pom.xml

  build:              # Job 2
    needs: test         # waits for test ✓
    steps:
      - run: mvn package -DskipTests
      - uses: actions/upload-artifact@v3

  deploy:             # Job 3
    needs: build        # waits for build ✓
    if: github.ref == 'refs/heads/main'
    steps:
      - run: cf push -f manifest.yml

Job 1: test

  • Runs on every push + PR
  • Fresh Ubuntu machine
  • mvn test → JUnit runs
  • Fail = everything stops

Job 2: build

  • needs: test — waits for test
  • mvn package → creates JAR
  • Uploads JAR as GitHub artifact

Job 3: deploy

  • needs: build
  • Only on push to main branch
  • Downloads JAR from build job
  • cf push -f manifest.yml

From zero to automated pipelines — hands-on guide

The Problem Without CI/CD

Imagine 5 developers working on the same codebase. Each writes code for a week, then they try to merge. Conflicts everywhere. Tests fail. Nobody knows whose code broke what. This is called integration hell.

😤 Without CI/CD

  • Someone manually runs tests
  • Takes hours — or gets forgotten
  • Bug found days later
  • Already reached production

✅ With CI/CD

  • Every push triggers tests automatically
  • Bug found in minutes
  • Never reaches production
  • Developer notified immediately

What is Jenkins?

Jenkins is an open-source automation server. It watches your Git repository and automatically runs your pipeline whenever code changes are pushed.

Think of Jenkins as a robot developer that never sleeps — it pulls your code, runs your tests, and tells you immediately if something broke.

😤 Without Jenkins

  • Developer pushes code
  • Someone manually runs tests
  • Takes hours / forgotten
  • Bug found days later

✅ With Jenkins

  • Developer pushes code
  • Jenkins detects the push
  • Runs tests in seconds
  • Bug found immediately

Jenkins Core Concepts

Job / Project

A configured task in Jenkins. Define WHAT to do. Jenkins does it when triggered.

Freestyle Pipeline

Build

One execution of a job. Builds are numbered #1, #2, #3...

GREEN = SUCCESS

RED = FAILURE

Pipeline

Sequence of stages. If any stage fails, subsequent stages are skipped.

Checkout → Build → Test → Deploy

Stage

Named section of the pipeline. Jenkins shows each stage's status separately.

Agent

The machine that runs the pipeline. agent any = use any available machine.

Jenkinsfile

Text file in your repo that defines the entire pipeline as code. Jenkins reads it automatically.

Pipeline as Code

Jenkinsfile — The Pipeline Definition

pipeline {
    agent any           // run on any available Jenkins agent

    stages {
        stage('Checkout') {
            steps { git branch: 'main', url: 'https://github.com/YOUR/repo.git' }
        }
        stage('Build') {
            steps {
                sh 'echo "Build stage running"'
                sh 'python3 --version'
            }
        }
        stage('Test') {
            steps { sh 'python3 test_calculator.py' }  // FAIL here = Red build, Deploy skipped
        }
        stage('Deploy') {
            steps { sh 'echo "Deploy placeholder"' }  // only runs if Test passes
        }
    }
}

Jenkinsfile — Every Keyword Explained

InstructionMeaning
pipeline {}The entire pipeline definition
agent anyRun on any available Jenkins machine
stages {}Container for all stages
stage('Name') {}A named step in the pipeline
steps {}Commands to run inside a stage
sh '...'Run a shell command on the agent
git branch: 'main', url: '...'Pull code from GitHub

Why keep Jenkinsfile in the repo? If Jenkins server crashes and config was only in the UI, everything is lost. With Jenkinsfile in the repo, you can recreate the pipeline on a new server in minutes.

calculator.py — The Application

def add(a, b):
    return a + b         # correct version

def subtract(a, b):
    return a - b

def multiply(a, b):
    return a * b

def divide(a, b):
    if b == 0:
        return None
    return a / b

Why this matters: When a developer accidentally changes return a + b to return a - b, the tests catch it immediately on the next push. Without CI, this bug might reach production.

Containers are like apartments in a building — separate living spaces, shared foundation.

Our Dockerfile — Stage 1: Build

# Stage 1 — compile the app using Maven + JDK
FROM maven:3.9-eclipse-temurin-17 AS build
# Start with a machine that has Maven and JDK 17 installed

WORKDIR /app
# Create /app folder and work inside it (like: mkdir /app && cd /app)

COPY pom.xml ./
RUN mvn dependency:go-offline -q
# Copy dependency list first, download all libraries
# Docker skips this step next time if pom.xml didn't change (caching)

COPY src ./src
RUN mvn package -DskipTests -q
# Copy source code, compile → produces devops-demo-app-1.0.0.jar

At this point: the JAR exists inside Stage 1. Stage 1 has Maven + JDK (~500 MB).

Our Dockerfile — Stage 2: Runtime

# Stage 2 — fresh start, JRE only, no build tools
FROM eclipse-temurin:17-jre
# New base image — just the JRE (runs Java, but can't compile)
# This is the image that gets deployed

WORKDIR /app

COPY --from=build /app/target/devops-demo-app-1.0.0.jar app.jar
# From Stage 1, take ONLY the JAR. Everything else is thrown away.

EXPOSE 8080
# Documents that this app listens on port 8080

ENTRYPOINT ["java", "-jar", "app.jar"]
# When the container starts, run: java -jar app.jar

Final image: JRE + JAR only (~180 MB). Maven and JDK are gone. Smaller = faster deploys.

Why Two Stages?

Stage 1 — Temporary
  • Maven 3.9
  • JDK 17 (full compiler)
  • Source code
  • Downloaded libraries

Size: ~500 MB

Gets thrown away after build

Stage 2 — Final Image ✓
  • JRE 17 (run only)
  • devops-demo-app.jar

Size: ~180 MB

This is what gets deployed

Analogy: you use a full workshop to build furniture, then deliver only the finished piece — not the entire workshop.
