⏱ Session 1 · What is DevOps?

The Problem — Dev vs Ops Silos

😤 Development Team

  • Goal: ship new features fast
  • Writes code on their laptop
  • Tests on their own environment
  • Says: "Works on my machine!"
  • Throws code over the wall to Ops
  • Moves on to next feature

😤 Operations Team

  • Goal: keep production stable
  • Receives code without warning
  • Environment is different from Dev
  • Says: "It's breaking our servers!"
  • Blames developers for bad code
  • Deployment takes days

Result Without DevOps

  • Releases once a month or less
  • Deployment takes 2-3 days manually
  • Bugs reach production frequently
  • Teams blame each other
  • On-call engineers panic every Friday

This is called "Integration Hell"

Teams build in isolation for weeks. When they finally combine their work — conflicts everywhere. Nobody knows whose change broke what. Untangling takes days.

The Restaurant Analogy

🍳 Old Way — Silos

Chefs (Dev) cook dishes and slide plates through a tiny window. Waiters (Ops) have no idea what's in them.

  • Customer complains — waiter blames chef
  • Chef says "It was fine when I made it"
  • New dishes take weeks to reach customers
  • Nobody shares responsibility

🤝 DevOps Way — One Team

Chefs and waiters work as one team. They designed the menu together.

  • Feedback from customers → chefs hear it directly
  • Automatic taste test before every dish leaves kitchen
  • New dish ready? Served within minutes
  • One team, one goal: happy customers
🍽️

Recipe = Code

🔪

Test kitchen = CI

🚀

Serving the dish = CD

Key insight: DevOps isn't just tools. It's a culture shift — shared ownership, shared responsibility, shared metrics. Tools enable it; culture makes it work.

⏱ Session 1 · What is DevOps?

What is DevOps?

DevOps is a culture, mindset, and set of practices that brings Development and Operations teams together — breaking down silos, automating the software delivery process, and enabling teams to build, test, and release software faster, more reliably, and continuously.

🤝

Collaboration

Dev and Ops share ownership of features from coding to production. Same team, same goals, same on-call.

🤖

Automation

Every manual step between code and production is automated — testing, building, deploying, monitoring.

🔁

Fast Feedback

Know within minutes if something broke. Don't wait days to find out. Small changes, frequent releases.

Remember: DevOps is NOT a job title. It's not "DevOps Engineer = Ops person who knows Docker." It's an organisation-wide philosophy. Dev + Ops + Security + QA — everyone participates.

⏱ Session 1 · Infinity Loop — Stage 1

📋 Stage 1 — Plan

What happens here?

  • Product team defines what to build next
  • Features broken into user stories
  • Work assigned to developers in sprints
  • Priorities set based on business value
  • Dependencies and risks identified

Tools

  • Jira — issue tracking, sprint planning
  • Confluence — documentation
  • Miro — whiteboarding
  • GitHub Issues — lightweight tracking

Agile Connection

Planning in DevOps is always Agile — 2-week sprints, not 6-month waterfall plans. Small work chunks, fast feedback.

SAP Context

SAP teams use Jira for sprint planning and GitHub Issues on github.tools.sap for tracking development work against code changes.

Why this matters: Monitor stage feeds back here. Production metrics, user complaints, and bug reports all become new Plan items. The loop closes.
⏱ Session 1 · Infinity Loop — Stage 2

💻 Stage 2 — Code

What happens here?

  • Developers write feature code
  • Work on isolated feature branches
  • Code reviewed by teammates via PRs
  • Every change tracked in Git
  • Commit messages document the "why"

Tools

  • VS Code / IntelliJ — IDE
  • Git — version control
  • GitHub / GitLab — code hosting

The trigger point: When a developer pushes code or merges a PR, the CI/CD pipeline fires automatically. Code stage is where the DevOps automation begins.
⏱ Session 1 · Infinity Loop — Stages 3 & 4

🔨 Stage 3 — Build  ·  🧪 Stage 4 — Test

🔨 Build

Transforms source code into a runnable artifact. One command, fully automated.

  • Compile source code
  • Resolve dependencies (libraries)
  • Package into JAR / WAR / Docker image
  • Generate build reports

Tools: Maven, Gradle, npm, webpack

Our command: mvn package

🧪 Test

Automatically verify the code works correctly. No humans needed.

  • Unit tests — test individual functions
  • Integration tests — test modules together
  • UI tests — test the browser flow
  • Security scans — check for vulnerabilities

Tools: JUnit, Mockito, Selenium, SonarQube

Our command: mvn test

Build fails? Pipeline stops. Nobody is notified to manually check. The pipeline itself sends a failure notification. Fix before moving on.
Tests fail? Bug caught here — before anyone sees it. Cost to fix here: 5 minutes. Cost to fix in production: hours + angry users.

📦 Release

The build artifact is versioned and made ready for deployment. This is the handoff from Dev to Ops.

  • Health check after deploy

Tools: Jenkins, GitHub Actions, Kubernetes, BTP CF

⚙️ Stage 7 — Operate  ·  📊 Stage 8 — Monitor

⚙️ Operate

Keep the application running smoothly in production — scale, manage, update infrastructure.

  • Auto-scaling when traffic spikes
  • Self-healing — restart crashed containers
  • Zero-downtime updates (rolling deploys)
  • Infrastructure as Code — reproducible

Tools: Kubernetes, Terraform, Ansible, BTP CF

Watch everything happening in production. Catch problems before users report them.

  • Logs — what happened, when, who triggered it

Tools: Prometheus, Grafana, ELK Stack, Dynatrace

⏱ Session 2 · Git's Role in DevOps

Why Git is the Foundation of DevOps

Git is the Starting Gun

Every DevOps automation begins with a Git event. Without Git, CI/CD cannot exist. The pipeline doesn't start because someone clicks a button — it starts because someone pushes code.

Single Source of Truth

  • Application code
  • Infrastructure code (Terraform)
  • Pipeline definitions (Jenkinsfile, YAML)
  • Configuration files (manifest.yml)
  • Documentation

Everything that affects your system lives in Git.

Without Git

  • No history — who changed what, when, why?
  • No collaboration — overwriting each other's work
  • No automation — nothing to trigger on
  • No rollback — can't go back to working version
The DevOps mantra: "If it's not in Git, it doesn't exist." Your pipeline YAML, your Dockerfile, your Kubernetes manifests — all in Git. Version controlled. Peer reviewed. Auditable.

How a PR Triggers the CI/CD Pipeline

1
Developer creates a feature branch

# works on feature/new-hello-message, not on main
2
Developer pushes and opens a Pull Request 
git push origin feature/new-hello-message
# Opens PR on GitHub → requests review from teammate
3
GitHub fires the CI pipeline automatically

GitHub Actions detects the PR event → runs test + build → posts result as a status check on the PR. Reviewer can see: ✅ All checks passed.

4
PR approved + merged to main → CD fires

Merge to main triggers the full pipeline including deploy. App goes live on BTP CF. Nobody manually did anything.

Main branch

  • Always deployable
  • Protected — no direct push
  • Only accepts PRs that pass CI

  • One branch per feature/bugfix
  • Short-lived — merge quickly
  • Isolated from other work

Pull Request

  • Code review gate
  • CI must pass to merge
  • Discussion, feedback, approval

GitOps — Taking Git Even Further

What is GitOps?

GitOps extends the "everything in Git" idea to infrastructure and deployments. The desired state of your entire system — what's deployed, how many replicas, which config — all declared in Git files.

GitOps principle

  • Git is the single source of truth for system state
  • Changes happen through Git — not manual commands
  • System automatically syncs to what Git says
  • Any drift from Git → automatically corrected

Example

You want to scale from 3 to 5 replicas in Kubernetes. Old way: run kubectl scale. GitOps way: change the number in k8s/deployment.yaml and push to Git. The system detects the change and scales automatically.

Tools

  • ArgoCD — most popular GitOps tool
  • Flux — Kubernetes GitOps
  • Both watch a Git repo and sync Kubernetes state

Why this matters for you: Our k8s/ folder in devops-demo-app has deployment.yaml and service.yaml. In a GitOps setup, pushing a change to these files would automatically update the live Kubernetes cluster.

⏱ Session 3 · CI/CD Concepts

What is Continuous Integration (CI)?

CI is the practice of automatically building and testing every code change the moment it's pushed to the shared repository — multiple times per day, every day.

The Problem CI Solves

  • 5 devs work in isolation 2 weeks
  • All merge at once — "integration hell"
  • Conflicts everywhere
  • Nobody knows what broke what
  • Takes 3 days to untangle

What CI Does Instead

  • Merge small, merge often
  • Every push → automatic build + test
  • Bug caught in minutes not days
  • Always know the code works
  • Developers stay in sync

3 Rules of CI

  • Every commit triggers the pipeline
  • Fix broken builds immediately
  • Software works ALL the time

"Finish First Before Start" — don't pile up uncommitted work

Baking analogy: Old way = bake the whole cake then find out the batter was wrong. CI = taste the batter before baking, adjust as you go. Catch problems early when they're cheap to fix.
⏱ Session 3 · CI/CD Concepts

What is Continuous Delivery vs Deployment (CD)?

Continuous Delivery

Code is always ready to deploy — but a human decides when to actually ship.

  • Pipeline runs automatically
  • Builds, tests, stages the release
  • Waits for human approval button
  • Human clicks "Deploy to Production"

Used in: banking, healthcare, regulated industries

Continuous Deployment

Code is automatically deployed to production the moment CI passes — no human in the loop.

  • Pipeline runs automatically
  • Builds, tests, deploys
  • No approval button
  • Live in production immediately

Used in: Netflix, Spotify, SaaS products

Why Does CI/CD Exist?

Without CI/CD

  • Releases once a month
  • Deploy on Friday night — fix all weekend
  • Manual testing takes weeks
  • Deployment steps documented in a 50-page runbook
  • One person knows how to deploy — what if they're on holiday?
  • Rollback means restoring from backup — hours
True story: A bank released once every quarter. 3 months of changes, deployed on a Saturday. Deployment took 8 hours. Every release was an emergency. The team called it "the most stressful day of the year." Every quarter.

With CI/CD

  • Deploy multiple times per day
  • Deploy on Tuesday morning — boring
  • Tests run in 3 minutes, automatically
  • Deploy = git push
  • Any developer can deploy — it's just a push
  • Rollback = redeploy previous artifact — 2 minutes

Anatomy of a CI/CD Pipeline

A pipeline is a sequence of automated stages. Each stage is a gate — fail one, stop everything.

Trigger
git push
→
Test
mvn test
→
Build
mvn package
→
Artifact
app.jar stored
→
Deploy
cf push

Trigger

What starts the pipeline. A push to main, a PR, a scheduled time, a manual button. In our pipeline: on: [push, pull_request]

Test → Build

Test first — if tests fail, no point building. Build creates the artifact. These are the CI stages. Always run on every push.

Artifact → Deploy

Artifact is the output — a JAR, a Docker image. Deploy pushes it to the environment. These are the CD stages. Only run on merge to main.

Key concept: Stages run in order. Stage 2 can't start until Stage 1 passes. This is the needs: keyword in GitHub Actions YAML. If Test fails → Build never runs → Deploy never runs → users never see broken code.

What is an Artifact?

Definition

An artifact is the built output of your code — the deployable package that contains everything needed to run your application.

  • Java app → .jar file
  • Java web app → .war file
  • Node app → node_modules/ + code
  • Any app → Docker image
  • Android app → .apk file

Our Artifact Today

mvn package
  ↓
app/target/devops-demo-app-1.0.0.jar

This JAR contains:
  - Compiled Java classes
  - Spring Boot runtime
  - All dependencies
  - Configuration files

Size: ~20 MB
Deployable: anywhere with Java 17

Build once

Same artifact deployed to Dev, QA, Production. Not rebuilt for each environment.

Store it

GitHub Actions uploads as artifact. JFrog/Nexus in enterprise. Always keep previous version for rollback.

Version it

1.0.0, 1.0.1, 1.1.0 — know exactly what's deployed where at any time.

⏱ Session 3 · Pipeline Anatomy

Pipeline YAML — The 4 Key Sections

# 1. TRIGGER — what fires the pipeline
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

# 2. JOB — a group of steps
jobs:
  test:
    runs-on: ubuntu-latest  # fresh Linux machine

  build:
    needs: test             # waits for test to pass

  deploy:
    needs: build            # waits for build to pass
    if: github.ref == 'refs/heads/main'

1. Trigger (on:)

Defines what event fires the pipeline. Push to main AND pull requests both trigger test + build. Only push to main triggers deploy.

2. Jobs + needs:

needs: creates a dependency chain. Test must pass before build starts. Build must pass before deploy starts. Sequential gates.

3. Steps inside a job

Each step is one action. uses: = use a pre-built action. run: = run a shell command. Steps run in order within a job.

4. Secrets (${{ secrets.X }})

Credentials stored encrypted in GitHub repo settings. Referenced by name in YAML. Never visible in logs or code.
