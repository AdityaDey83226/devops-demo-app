The Problem Without CI/CD

Imagine 5 developers working on the same codebase. Each writes code for a week, then they try to merge. Conflicts everywhere. Tests fail. Nobody knows whose code broke what.

This is called integration hell.

😤 Without CI/CD

  • Someone manually runs tests
  • Takes hours — or gets forgotten
  • Bug found days later
  • Already reached production

✅ With CI/CD

  • Every push triggers tests automatically
  • Bug found in minutes
  • Never reaches production
  • Developer notified immediately

CI vs CD — What's the Difference?

CI — Continuous Integration

Every time code is pushed to GitHub, automatically:

  • Pull the latest code
  • Build the application
  • Run all tests
  • Report Pass or Fail immediately

Goal Catch bugs early — within minutes of pushing, not days later.

CD — Continuous Delivery/Deployment

After CI passes, automatically:

  • Package the application
  • Deploy to staging or production
  • Run smoke tests
  • Notify the team

Goal Ship code to users faster with less manual effort.

What is Jenkins?

Jenkins is an open-source automation server. It watches your Git repository and automatically runs your pipeline whenever code changes are pushed.

Think of Jenkins as a robot developer that never sleeps — it pulls your code, runs your tests, and tells you immediately if something broke.

😤 Without Jenkins

  • Developer pushes code
  • Someone manually runs tests
  • Takes hours / forgotten
  • Bug found days later

✅ With Jenkins

  • Developer pushes code
  • Jenkins detects the push
  • Runs tests in seconds
  • Bug found immediately

Both do the same job — automate build, test, deploy. The difference is where they run and how they're configured. In this training we use Jenkins for the CI/CD engine and GitHub Actions for the BTP CF pipeline.

Jenkins Cons → Fixed by GitHub Actions

Then why does Jenkins still exist? Self-hosted servers, air-gapped environments, regulated industries, not on GitHub. In SAP — GitHub Actions is disabled on github.tools.sap at enterprise level, so Jenkins or SAP CI/CD Service is used instead.

Core Concepts

Job / Project

A configured task in Jenkins. You define WHAT to do. Jenkins does it when triggered.

Freestyle Pipeline

Build

One execution of a job. Builds are numbered #1, #2, #3...

GREEN = SUCCESS

RED = FAILURE

Pipeline

A sequence of stages that run in order. If any stage fails, subsequent stages are skipped.

Checkout → Build → Test → Deploy

Stage

A named section of the pipeline. Jenkins shows each stage's status separately in the UI.

Agent

The machine that runs the pipeline. agent any = use any available machine.

Jenkinsfile

A text file in your repo that defines the entire pipeline as code. Jenkins reads it automatically.

calculator.py — The Application

def add(a, b):
    return a + b         # correct version

def subtract(a, b):
    return a - b

def multiply(a, b):
    return a * b

def divide(a, b):
    if b == 0:
        return None      # avoid division by zero
    return a / b

Why this matters in CI: When a developer accidentally changes return a + b to return a - b, the tests catch it immediately on the next push. Without CI, this bug might reach production.

test_calculator.py — The Tests

import calculator              # import the application module

# assert <condition> → fails with AssertionError if condition is False
assert calculator.add(2, 3) == 5          # 2+3 must equal 5
assert calculator.subtract(5, 3) == 2     # 5-3 must equal 2
assert calculator.multiply(2, 3) == 6     # 2×3 must equal 6
assert calculator.divide(6, 3) == 2       # 6÷3 must equal 2

print("All tests passed")              # only prints if all assertions pass

subtract(5,3)==25, 32subtraction logic error
multiply(2,3)==62, 36multiplication logic error
divide(6,3)==26, 32division logic error

Jenkinsfile — The Pipeline Definition

pipeline {
    agent any          // run on any available Jenkins agent

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main', url: 'https://github.com/YOUR/repo.git'
            }    // pull latest code from GitHub
        }
        stage('Build') {
            steps {
                sh 'echo "Build stage running"'
                sh 'python3 --version'   // verify environment
            }
        }
        stage('Test') {
            steps {
                sh 'python3 test_calculator.py'  // FAIL here = Red build, Deploy skipped
            }
        }
        stage('Deploy') {
            steps {
                sh 'echo "Deploy stage placeholder"'
            }   // only runs if Test passes
        }
    }
}

Jenkinsfile — Every Keyword Explained

InstructionMeaning
pipeline {}The entire pipeline definition
agent anyRun on any available Jenkins machine
stages {}Container for all stages
stage('Name') {}A named step in the pipeline
steps {}Commands to run inside a stage
sh '...'Run a shell command on the agent
git branch: 'main', url: '...'Pull code from GitHub

Why keep Jenkinsfile in the repo? If Jenkins server crashes and the config was only in the UI, you lose everything. With Jenkinsfile in the repo, you can recreate the pipeline on a new Jenkins server in minutes.

Task 3 — Trigger a Red Build (Bug)

1

Enable SCM Polling

calculator-pipeline → Configure → Triggers → check Poll SCM → Schedule: * * * * * (every minute) → Save

2

Introduce a bug in calculator.py

def add(a, b):
    return a - b    # BUG: should be a + b
git add calculator.py
git commit -m "Added fault code"
git push origin main

Wait up to 1 minute. Jenkins detects the push, runs the pipeline automatically.

Expected result: Test stage FAILS → AssertionError because add(2,3) returns -1 not 5. Deploy stage is skipped. Build = RED ✗

Task 3 — Fix the Bug → Green Build

3

Fix calculator.py

def add(a, b):
    return a + b    # FIXED
git add calculator.py
git commit -m "Fixed add function"
git push origin main

Wait up to 1 minute. Jenkins detects the fix and re-runs the pipeline.

Expected result: All stages pass. Test stage prints "All tests passed". Deploy stage runs. Build = GREEN ✓
